# Job Search Agent — System Overview & Cross-Cutting Decisions
#### tl;dr

The Job Search Agent is a personal, mostly-autonomous pipeline that finds in-scope job postings, captures them once into a single hosted database, lets the user decide fit, and turns each *Apply* into an application packet (with a checklist for the user's own resume revision) and a tracker row — improving its own search prompt with use. This document is the **index** to the PRD set: it owns the doc map, the dependency tiers, and the **cross-cutting decision registry** (`XC-*`). It defines those shared decisions once so every other PRD can reference them in a single token rather than restating them ("one fact, one home").

-----
#### Dependency tiers

Ordered by what must exist before what — useful for reading, and a record of how the system composes.

- **Tier 0 — Foundation:** *06 Platform* (accounts, secrets, the shared DB) and *02 Data* (schema + connection). Everything depends on these; they depend on nothing else in the set.
- **Tier 1 — Contracts:** the **output JSON schema** and **canonical-URL idempotency** (01), and the **`postings` columns + query surface** (02). These are the interfaces every later stage builds against — settled first (`XC-3`).
- **Tier 2 — Ingest:** *01 Agentic Job Search* (produces + captures rows). Runs against the Tier-1 contracts.
- **Tier 3 — Human decision:** *03 Fit Review* (consumes captured rows, produces decisions + feedback). Can be built in parallel with 04, since 04 consumes its *output* (`decision = Apply`), not its internals.
- **Tier 4 — Outputs:** *04 Application Outputs* (consumes Apply rows). Depends on 02's queues and 01's capture; parallel to 03.
- **Tier 5 — Learning:** *05 Dynamic Development* (consumes accumulated decisions). Depends on 03's feedback; changes 01's search fragments via a proposal the user resolves and accepts. Can be developed last and independently — it reads the others' *outputs*.

#### Cross-cutting decision registry

Each decision below is stated once here and referenced by ID from the PRDs it touches. When one changes, edit it here and propagate.

- **`XC-1` — Cloud/local split.** Only Steps 1–2 (search + insert) run in the cloud, headless on a scheduled Fly.io machine. Everything else — Steps 3–5 (review, packets and checklists, Sheet), the learning loop, and deployment itself (`jsa deploy`) — runs locally. There is no CI: nothing depends on a git push, and the repo holds only app code. This drives where credentials live (AI model API keys = Fly secrets + local `.env`; Google OAuth and Fly auth = local only), inherited from the environment, never passed by code — with one exception: the Claude search runner hands its own API key (`JSA_SEARCH_ANTHROPIC_API_KEY`) to the CLI it spawns, so search runs always bill to an API key while local Claude commands use whichever credential the user's `.env` holds. No credential ever passes through an agent transcript. *Touches: 01, 03, 04, 05, 06.*
- **`XC-2` — One hosted DB, no copies.** The JD database is one Turso (hosted libSQL) instance; cloud cron and local sessions connect to the *same* copy. A `file:` URL is throwaway dev only — never a second store that can diverge. *Touches: 01, 02, 03, 04, 05, 06.*
- **`XC-3` — Single-mechanism idempotency; no dedup subsystem.** Dedup is exactly one thing: URL canonicalization into a `UNIQUE canonical_url` + `INSERT … ON CONFLICT DO NOTHING RETURNING id`. Because the prompt requires index-linked ATS URLs, agents converge on the same canonical URL, so this also covers cross-source duplicates. No second dedup stage, no embeddings. *Touches: 01, 02.*
- **`XC-4` — DB is the source of truth for posting data; the Sheet is its projection + the user's application-state workspace.** Agent-written Sheet columns (ID…Date Added) are a view the agent appends and may refresh from the DB; user columns (Date Applied, Status) are the only application state, written only by the user and read by the agent only to scope its own work. Authority never flows Sheet→DB; application state is never mirrored into the DB. *Touches: 02, 04.*
- **`XC-5` — Four supported ATS = the platforms the pipeline can verify; the pipeline, not the agent, guarantees liveness and recency; capture ≠ liveness.** Greenhouse, Lever, Ashby, Rippling. On the search path the pipeline fetches each emitted posting's board index (once per board per run; plus the detail record for Rippling) before insert, and inserts only postings that are on the index and whose ATS timestamp falls inside the search window (with 24h slack). Everything else is dropped and recorded with its reason (`not_on_index`, `out_of_window`, `unverifiable` when a needed fetch failed, `unsupported` when the URL is off the four), whichever runner, model, or preset produced it. A platform that returns no timestamp passes as `verified_no_date` with a warning, so an undocumented field disappearing never silently removes a whole platform. The agent's own liveness and recency work is an efficiency, never the guarantee. A searched URL off the four is never JSON-LD-enriched. The manual-add path *does* fall back to schema.org JSON-LD for capture (order: supported fetcher → JSON-LD → `NULL`), because the user has vouched for that posting — but a successful capture is never evidence a posting is live. *Touches: 01, 03, 04.*
- **`XC-6` — Full-JD capture is best-effort and never a gate.** A failed fetch degrades to `NULL jd_markdown` and never excludes a row at insert; on refetch a failed fetch leaves the row *completely untouched* (never trade a good capture for a blip). *Touches: 01, 04.*
- **`XC-7` — The learning loop is incremental via DB run-records, and the artifacts stay standalone.** The `prompt_refinement_runs` cutoff scopes each run; only completed runs are recorded, so an errored run's inputs are reconsidered. The search fragments carry no watermark or ground-truth reference — incrementality lives in the DB, not the artifact. *Touches: 02, 05.*
- **`XC-8` — Turso autocommit via `isolation_level = None`.** The `turso_serverless` client's DB-API `autocommit` attribute is a silent no-op; only `isolation_level = None` enables per-statement autocommit. Without it every write opens an implicit transaction that `close()` rolls back — a silent-data-loss trap. *Touches: 02 (owner), 01, 03, 04.*
- **`XC-9` — Deterministic seams stay I/O-free; no agent-authored tests.** Pure logic (`prompts.assemble`, `cron_due`, `verify.classify`, `canonicalize`, `naming`, `search.parse`, `ats.resolve`, `review.parse_feedback_entry`, `tracker.build_row`, `manual.company_from_board`, `resume.render_resume_text`, `packet.resume_file_stem`, `refine.conflict_view`) is kept side-effect-free so it is testable from outside; agentic steps (the resume checklist, refine) are verified against real-world checks, not co-written tests. *Touches: all.*
- **`XC-10` — `added_to_tracker` is the Step 4/5 completion guard, not directory-exists.** `jsa packet` uses a fail-if-exists mkdir as a cheap safety, but `jsa generate` re-enters a bare directory (left by `jsa packet`, an interrupted run, or a refetch rename) because the real completion signal is `added_to_tracker`. *Touches: 04.*
- **`XC-11` — The user surface is one gitignored `profile/` directory; nothing user-specific lives in `src/`, the app prompts, or the PRDs.** Inputs sort into three kinds with three homes: *secrets and machine-local tool paths* → the environment (`.env`, Fly secrets); *scalar user config* (name, tracker id, packets path, Fly app, cadence, timezone) → TOML in the profile; *user prose and judgment* (who the candidate is, what they want) → Markdown fragments filled into named slots of the app prompts (`XC-13`), alongside the user's single base resume. The whole of `profile/` (`JSA_PROFILE_DIR` overrides the location) is gitignored; the committed `profile.example/` mirrors its exact shape with a fictional candidate, and setup starts by copying it. **The directory boundary is the sensitivity boundary:** `profile/search/` is the only profile content that leaves the machine (baked into the Fly image by `jsa deploy`); identity config and the base resume never do. A fork edits `profile/` and nothing else — a need to edit an app prompt to fit one candidate means a slot is missing. The layout is owned by PRD 06. *Touches: 01, 04, 05, 06.*
- **`XC-12` — Headless agent runs share one scaffold (`agent.py`).** `collect_final_text`/`run_agent` drive the Claude Agent SDK message loop, collect the final text, and raise the caller's error class on an `is_error` result so an errored run is never recorded. `generate` and `refine` supply only their tools and error class; their model and effort come from the profile (`XC-14`). *Touches: 04, 05.*
- **`XC-13` — Every app prompt is an app template plus named user slots.** Each prompt is a candidate-agnostic template shipped in the package (`src/jsa/prompts/`) with `{{SLOT}}` markers placed by the template's author — user content is never merely appended, because where text sits in a prompt changes what it means. One pure function, `prompts.assemble(template, values)`, fills every marker from its declared source: a run-time value (`{{SEARCH_WINDOW}}`, `{{JOB_DESCRIPTION}}`), a profile fragment, or a profile config value; file reading happens outside it. Each profile slot is declared **required** (a missing or empty source raises before any model call) or **optional** (degrades to a fixed placeholder note), and any marker left unfilled after assembly raises, so a template and a profile can never silently disagree. Each template states, beside each user slot, the **precedence** between the user's content and the surrounding machinery (the search template's liveness gates and output contract override any fragment). Slots split rules at *policy vs content*: the template owns what a kind of rule does (negative signals never exclude; hard exclusions are title-level only; an unstated criterion never excludes); the fragment owns which rules exist. Each prompt's slot table lives in its owning PRD (01 search, 04 resume checklist, 05 refine). *Touches: 01, 04, 05, 06.*
- **`XC-14` — The app owns tool calling; the user owns model and effort.** Which model runs an agent, and how hard it thinks, determines output quality, and the app has no opinion on that: every agent's model and effort (the Claude and Gemini search runners in `profile/search/search.toml`; the resume checklist and refine in `profile/config.toml`) is profile config with no app-maintained list of allowed values. The app validates only that values are well-formed, always passes effort explicitly rather than inheriting a model's default, and records the resolved model and effort in the search telemetry. What the app does own is everything that decides whether tool calls happen and are checked: each agent's tool set, turn/step/time limits, permission mode, stream handling, output contracts, and liveness verification (`XC-5`). Example defaults and recommendations live as comments in `profile.example/`, never as enforcement. **The one exception is the user's choice:** the Perplexity runner is pinned wholesale to the `xhigh` preset (which bundles model, tools, and step budget), so it has no settings; the model it resolves to is recorded, not configured. *Touches: 01, 02, 04, 05, 06.*
