# Job Search Agent — System Overview & Cross-Cutting Decisions
#### tl;dr

The Job Search Agent is a personal, mostly-autonomous pipeline that finds in-scope job postings, captures them once into a single hosted database, lets the user decide fit, and turns each *Apply* into an application packet (with a checklist for the user's own resume revision, and an optional ATS redline of the resume's wording that the user reviews in Word) and a tracker row — improving its own search prompt with use. This document is the **index** to the PRD set: it owns the doc map, the dependency tiers, and the **cross-cutting decision registry** (`XC-*`). It defines those shared decisions once so every other PRD can reference them in a single token rather than restating them ("one fact, one home").

-----
#### Dependency tiers

Ordered by what must exist before what — useful for reading, and a record of how the system composes.

- **Tier 0 — Foundation:** *06 Platform* (accounts, secrets, the shared DB) and *02 Data* (schema + connection). Everything depends on these; they depend on nothing else in the set.
- **Tier 1 — Contracts:** the **output JSON schema** and **canonical-URL idempotency** (01), and the **`postings` columns + query surface** (02). These are the interfaces every later stage builds against — settled first (`XC-3`).
- **Tier 2 — Ingest:** *01 Agentic Job Search* (produces + captures rows). Runs against the Tier-1 contracts.
- **Tier 3 — Human decision:** *03 Fit Review* (consumes captured rows, produces decisions + feedback). Can be built in parallel with 04, since 04 consumes its *output* (`decision = Apply`), not its internals.
- **Tier 4 — Outputs:** *04 Application Outputs* (consumes Apply rows). Depends on 02's queues and 01's capture; parallel to 03.
- **Tier 5 — Learning:** *05 Dynamic Development* (consumes accumulated decisions). Depends on 03's feedback; changes 01's search fragments via a proposal the user resolves and accepts. Can be developed last and independently — it reads the others' *outputs*.

#### Cross-cutting decision registry

Each decision below is stated once here and referenced by ID from the PRDs it touches. When one changes, edit it here and propagate.

- **`XC-1` — Cloud/local split.** Only Steps 1–2 (search + insert) run in the cloud, headless on a scheduled Fly.io machine. Everything else — Steps 3–5 (review, packets and checklists, Sheet), the learning loop, and deployment itself (`jsa deploy`) — runs locally. Deployment is the user's local `jsa deploy`: no product behavior depends on a git push or a CI/CD pipeline. This drives where credentials live (AI model API keys = Fly secrets + local `.env`; Google OAuth and Fly auth = local only), inherited from the environment, never passed by code — with one exception: when `JSA_SEARCH_ANTHROPIC_API_KEY` is set, the Claude search runner hands it to the CLI it spawns as its only credential. Production (the Fly machine and the owner's hand runs) sets it, so production searches bill to an API key. Development leaves it unset, so the runner inherits the environment's Claude credential like every other Claude command and development never needs an API key. No credential ever passes through an agent transcript. *Touches: 01, 03, 04, 05, 06.*
- **`XC-2` — One hosted DB, no copies.** The JD database is one Turso (hosted libSQL) instance; cloud cron and local sessions connect to the *same* copy. A `file:` URL is throwaway dev only — never a second store that can diverge. *Touches: 01, 02, 03, 04, 05, 06.*
- **`XC-3` — Single-mechanism idempotency; no dedup subsystem.** Dedup is exactly one thing: URL canonicalization into a `UNIQUE canonical_url` + `INSERT … ON CONFLICT DO NOTHING RETURNING id`. Because every path stores the employer's own posting URL — on a supported ATS, the posting's ATS URL in the one form PRD 01's wire contract fixes; under `best_effort`, the employer's own page elsewhere; never an aggregator's, which manual add refuses too — agents and the user converge on the same canonical URL, so this also covers cross-source duplicates. No second dedup stage, no embeddings. *Touches: 01, 02, 03.*
- **`XC-4` — DB is the source of truth for posting data; the Sheet is its projection + the user's application-state workspace.** Agent-written Sheet columns (ID…Date Added) are a view the agent appends and may refresh from the DB; user columns (Date Applied, Status) are the only application state, written only by the user and read by the agent only to scope its own work. Authority never flows Sheet→DB; application state is never mirrored into the DB. *Touches: 02, 04.*
- **`XC-5` — The pipeline, not the agent, guarantees liveness; the user's `verification.mode` decides which platforms it admits; capture ≠ liveness.** Four supported ATS — Greenhouse, Lever, Ashby, Rippling — are the platforms whose own job index the pipeline can query. On the search path, in either mode, each emitted posting on one of the four is checked before insert against its board index (fetched once per board per run; plus the detail record for Rippling), and only postings on the index whose ATS timestamp falls inside the search window (with 24h slack) are inserted. `[verification] mode` in `profile/search/search.toml` sets what happens to everything else. Under `strict`, a URL off the four is dropped as `unsupported`. Under `best_effort`, an employer posting page on any other platform is admitted when one fetch of the page shows no sign the job is closed (an error status, a redirect away from the posting, an expired `validThrough`), and its recency is checked against the page's schema.org `datePosted` when it has one; without one, its recency rests on the agent's claim. Aggregator URLs are never admitted. Every dropped posting is recorded with its reason (`aggregator`, `unsupported`, `unverifiable` when a needed fetch failed, `not_on_index`, `page_closed`, `out_of_window`), whichever runner, model, or preset produced it. A posting that passes without a usable timestamp (`verified_no_date`, `reachable_no_date`) is inserted with a warning, so an undocumented field disappearing never silently removes a whole platform. The page check is weaker than an index check — a page can keep answering after its job closes — and that is the price of `best_effort`'s reach. The agent's own liveness and recency work is an efficiency, never the guarantee. Wherever a posting off the four is admitted — the search path under `best_effort`, and the manual-add path, where the user has vouched for the posting — capture falls back to the page's schema.org `JobPosting` data (order: supported fetcher → `JobPosting` data → `NULL`). A successful capture is never evidence a posting is live. Liveness is checked again wherever a human is about to spend time on a stored posting — when review starts and before a packet is built — and a posting found closed is retired without a decision (PRD 01). *Touches: 01, 02, 03, 04, 06.*
- **`XC-6` — Full-JD capture is best-effort and never a gate.** A failed fetch degrades to `NULL jd_markdown` and never excludes a row at insert; on refetch a failed fetch leaves the row *completely untouched* (never trade a good capture for a blip). *Touches: 01, 04.*
- **`XC-7` — The learning loop is incremental via DB run-records, and the artifacts stay standalone.** The `prompt_refinement_runs` cutoff scopes each run; only completed runs are recorded, so an errored run's inputs are reconsidered. The search fragments carry no watermark or ground-truth reference — incrementality lives in the DB, not the artifact. *Touches: 02, 05.*
- **`XC-8` — Turso autocommit via `isolation_level = None`.** The `turso_serverless` client's DB-API `autocommit` attribute is a silent no-op; only `isolation_level = None` enables per-statement autocommit. Without it every write opens an implicit transaction that `close()` rolls back — a silent-data-loss trap. *Touches: 02 (owner), 01, 03, 04.*
- **`XC-9` — Deterministic logic stays I/O-free, every outside dependency is replaceable, and tests are never co-written with the code.** The logic that decides — prompt assembly, the cron gate, verification classification, URL canonicalization, filesystem-safe naming, search-output parsing, ATS URL resolution, `JobPosting` extraction, review-feedback parsing, tracker row building, company-from-board derivation, resume rendering, packet and resume file naming, redline validation and tracked-change writing, and the refine conflict view — is side-effect-free, so it is testable from outside without the network or a database. Every call to the outside world goes through one replaceable point per kind: HTTP, the Claude Agent SDK (`XC-12`), the Gemini client, each external CLI (by its env-var path override, PRD 06), and the database (PRD 02). Agentic steps (the search runners, the resume checklist, the redline's proposals, refine) are verified against real-world checks, not tests co-written with them. *Touches: all.*
- **`XC-10` — `added_to_tracker` is the Step 4/5 completion guard, not directory-exists.** `jsa packet` skips a packet directory that already exists, as a cheap safety, but `jsa generate` re-enters a bare directory (left by `jsa packet`, an interrupted run, or a refetch rename) because the real completion signal is `added_to_tracker`. *Touches: 04.*
- **`XC-11` — The user surface is one gitignored `profile/` directory; nothing user-specific lives in `src/`, the app prompts, or the PRDs.** Inputs sort into three kinds with three homes: *secrets and machine-local tool paths* → the environment (`.env`, Fly secrets); *scalar user config* (name, tracker id, packets path, Fly app, cadence, timezone) → TOML in the profile; *user prose and judgment* (who the candidate is, what they want) → Markdown fragments filled into named slots of the app prompts (`XC-13`), alongside the user's single base resume. The whole of `profile/` (`JSA_PROFILE_DIR` overrides the location) is gitignored; the committed `profile.example/` mirrors its exact shape with a fictional candidate, and setup starts by copying it. **The directory boundary is the sensitivity boundary:** `profile/search/` is the only profile content that leaves the machine (baked into the Fly image by `jsa deploy`); identity config and the base resume never do. A fork edits `profile/` and nothing else — a need to edit an app prompt to fit one candidate means a slot is missing. The layout is owned by PRD 06. *Touches: 01, 04, 05, 06.*
- **`XC-12` — Every headless Claude run shares one agent loop.** The Claude search runner, the resume checklist, and refine all drive the Claude Agent SDK through one shared loop. It collects the final text, raises on an error result so an errored run is never recorded, and is the app's only call into the SDK (the test seam, `XC-9`). Each caller supplies only its prompt and its app-owned tools and limits; model and effort come from the profile (`XC-14`). The search runner also observes each message for its live trace (PRD 01). *Touches: 01, 04, 05.*
- **`XC-13` — Every app prompt is an app template plus named user slots.** Each prompt is a candidate-agnostic template shipped with the app, with `{{SLOT}}` markers placed by the template's author — user content is never merely appended, because where text sits in a prompt changes what it means. One pure assembly step fills every marker from its declared source: a run-time value (`{{SEARCH_WINDOW}}`, `{{JOB_DESCRIPTION}}`), a profile fragment, or a profile config value; file reading happens outside it. Each profile slot is declared **required** (a missing or empty source raises before any model call) or **optional** (degrades to a fixed placeholder note), and any marker left unfilled after assembly raises, so a template and a profile can never silently disagree. Each template states, beside each user slot, the **precedence** between the user's content and the surrounding machinery (the search template's liveness gates and output contract override any fragment). Slots split rules at *policy vs content*: the template owns what a kind of rule does (negative signals never exclude; hard exclusions are title-level only; an unstated criterion never excludes); the fragment owns which rules exist. Each prompt's slot table lives in its owning PRD (01 search, 04 resume checklist and redline, 05 refine). *Touches: 01, 04, 05, 06.*
- **`XC-14` — The app owns tool calling; the user owns model and effort.** Which model runs an agent, and how hard it thinks, determines output quality, and the app has no opinion on that: every agent's model and effort (the Claude search runner in `profile/search/search.toml`; the resume checklist and refine in `profile/config.toml`) is profile config with no app-maintained list of allowed models. The one agent that isn't headless, the interactive `/redline` proposal (PRD 04), runs on whatever model and effort the user's Claude Code session has. The app validates only form (effort must be one of the provider's effort levels), always passes effort explicitly (so a model that takes no effort setting is not supported) rather than inheriting a model's default, and records the resolved model and effort in the search telemetry. What the app does own is everything that decides whether tool calls happen and are checked: each agent's tool set, turn/step/time limits, permission mode, stream handling, output contracts, and how liveness verification works (`XC-5`); which postings verification admits is the user's `verification.mode`. Example defaults and recommendations live as comments in `profile.example/`, never as enforcement. **Two search runners are pinned, by the user's choice,** because each has only one setting that works for this search: the Perplexity runner wholesale to the `xhigh` preset (which bundles model, tools, and step budget), and the Gemini runner to the `deep-research-preview-04-2026` agent. Neither has settings; what each ran is recorded, not configured. *Touches: 01, 02, 04, 05, 06.*
